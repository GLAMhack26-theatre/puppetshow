# Puppetshow – SKKG Marionetten Theater (architecture plan)

## Context

GLAM hackathon 2026: bring the marionette paper theatre back into 3D. On a central, room-filling stage, the visitor plays a scene interactively with a rigged marionette controlled by gestures. The marionette can hold, throw and drop objects.

The repo is empty apart from the README; this doc defines the setup and architecture to build on.

## Decisions

| Topic | Decision |
|---|---|
| Rendering | three.js (the version bundled by IWSDK), `GLTFLoader`; no R3F |
| Game engine | **Meta IWSDK** (`@iwsdk/core`, MIT) in browser mode: `World.create(container, { xr: false })`. WebXR later via `xr: { offer: … }` |
| Physics | **Rapier** (`@dimforge/rapier3d-compat`) as our own system; IWSDK physics stays off (`features.physics: false`) |
| Gestures | MediaPipe (`@mediapipe/tasks-vision`: HandLandmarker + GestureRecognizer) |
| Targets | Phone and desktop with a webcam first, the phone running everything itself. VR later |
| Multiplayer | Several players on one stage, joined by a secret room id in the URL. **Trystero** (WebRTC data channels; peers meet over public Nostr relays, no server of our own). One host device simulates, the others send input and show poses (section 3.3) |
| Audio | Web Audio; background music and excerpts **streamed from archive.org** (netlabel releases, `assets/sounds/archive.json`); effects as CC0 samples + **ZzFX**; physics sounds from collision starts, stereo-panned. Music and effects each have a button, both off at every load |
| Tooling | TypeScript + Vite + HTTPS, run with npm (`npm run dev`, `npm run dev:https` for phones on the LAN); the app is served directly by Vite (no proxy). Docker Compose is set aside for now (later) |
| Assets | Sources committed in `/assets`, grouped by source, imported directly by Vite (`?url`, `import.meta.glob`); large files on external storage, downloaded by hand into `assets/external/` (git-ignored). A `convert` service that optimizes them into `/public` is planned for later |
| Fonts | Geist Sans + Geist Serif (OFL), self-hosted in `assets/fonts/`; used by the presentation so far |
| Exit | Back to the title screen |
| Later | WebXR 3DoF/6DoF, an AI player and audience directions over the room (section 3.3), LiteRT-LM |

Background: other engines and physics libraries were also evaluated.
- **Engines:** Needle Engine (not MIT), Houseki (GPL), elixr, Meep (archived), LittleJS (2D only), and our own thin engine.
- **Physics:** Rapier, Jolt, cannon-es and Havok. IWSDK ships Havok, but its physics API only covers rigid bodies: no joints, no sensors, no collision events, and the Havok instance is private (probably in a worker). The marionette needs joints and collision events (and had sensors in its hands until they became magnets, §3.2, 4), so Rapier runs as our own system.

## 1. Engine use (IWSDK)

**From IWSDK:**
- the ECS
- the render loop and scene
- spatial audio
- `PanelUI` / `ScreenSpace` UI
- canvas pointer, keyboard and gamepad input
- the Vite dev plugin (`@iwsdk/vite-plugin-dev`)
- later: XR input and the emulator

**Our own:**
- the stage camera (fixed or orbit; IWSDK leaves the camera to the app)
- all control input
- physics: `RapierSystem` (fixed 60 Hz step, poses synced to entities through `PhysicsLink`)
- the puppet rig, strings and grab: we write our own `GrabSystem`, because IWSDK's near-field grab is XR-only and grabbing here is done by the puppet's hands, not the user's

**Systems:**
- **Input:** `MediaPipeInputSystem`, `PhoneInputSystem` and `MouseInputSystem` all write `ControlInput`. `XRInputSystem` comes later. Every puppet has its own `ControlInput`; with several players the others' are filled from the network (`src/net/`, section 3.3).
- **Puppet:** `PuppetRigSystem` (physics pose → `SkinnedMesh` bones), `StringSystem` (constraint lengths + rendering the strings), `GrabSystem`.
- **Stage and scenes:** `SpotlightSystem`, `LightingSystem`, `AudioSystem`, `SceneFlowSystem` (Title ↔ Main).

**Components:** `Puppet`, `StringAttachment`, `Prop` (grabbable/throwable), `HangingLetter`, `Spotlight`.

### Phase 0 spike (½ day)
1. `xr: false` on a real phone (iOS Safari, Android Chrome): frame rate, bundle size, touch input, and the camera running together with MediaPipe.
2. **Rapier in the IWSDK loop:** fixed timestep, pose sync, rope joints for strings, spherical joints for limbs, grab with a sensor and a fixed joint. (IWSDK's own physics was ruled out before the spike.)
3. Plain three.js next to the ECS: raw `SkinnedMesh` bones, `TextGeometry`, `PositionalAudio`.
4. Does a custom system (MediaPipe) fit cleanly into the IWSDK loop?

If items 1 or 2 fail, the fallback is our own thin engine with the same split into systems and components.

## 2. Scenes & gameplay

**Title screen**
- "SKKG Marionetten Theater": each letter is a `TextGeometry` mesh in Geist Serif. The font is converted to typeface JSON (by the converter, once it exists).
- Each letter hangs on strings (Rapier rope joints) and sways. Pointer or hand movement pushes the letters.
- The **Play** button opens the main scene. It also unlocks audio and asks for the camera and motion-sensor permissions, because iOS only grants these after a user gesture.

**Main scene**
- At start the main curtain (`assets/stage_parts/Main_Curtain.glb`, `src/stage/main-curtain.ts`) hangs right in front of the camera and covers the whole screen at any aspect ratio, with a light cloth wobble (shader). Two seconds after start three signs (`src/stage/signs.ts`, the plays to choose from: `Sign_Haensel`, `Sign_Froschkoenig`, `Sign_Impro` in `assets/stage_parts/`) drop in one after another in a loose, slightly tilted row in front of it, overshoot and settle, and cast soft fake shadows on it (blurred silhouette quads, no shadow map). Hover enlarges a sign; a click on a sign raises the curtain, and the signs go up with it. Every further play in `assets/plays/` (made with the director bar) gets a sign painted at runtime (canvas texture: cardboard with a wooden lath, its name in hand-painted capitals, "in N Szenen"); they hang three to a row behind the three painted ones, and a golden **mehr** arrow under the signs pulls the next row down (**zurück** the previous one). The list is read anew each time the choice is shown. The same click starts the camera and MediaPipe hand control (`src/input/mediapipe.ts`): it is the user gesture camera access needs. Without a camera (or permission) the mouse keeps control; a **Kamera starten** button in the debug panel starts it by hand.
- **Impro mode** (the `Sign_Impro` sign, `src/impro/impro.ts`): once the curtain is up, round icon buttons (`assets/ui/icon-*.png`) appear at both screen edges, two per side: left **Requisiten** and **Sound**, right **Hintergrund** and **Licht**. Each side has one panel with a page per button; the buttons belong to the panel and ride along at its scalloped edge (closed, the panel stays out just far enough to keep them at the screen edge), the chosen one with a gold ring, and a golden X without background under them closes it. Licht holds the light desk on a paper sheet (see Lighting scenes below): the lighting scene of the stage and its sliders; Sound lists the archive.org excerpts (see Sound below). The **Hintergrund** page is a panel from the right (a quarter of the screen width, at least 240 px for phones): a starry night sky with a scalloped gold edge, on which the painted backdrops are paper cards travelling along a curve while scrolling, the middle one biggest (`src/impro/backdrop-slider.ts`, look tuned in its `SLIDER` constants, no settings UI). The cards are the painted backdrops (`assets/stage_parts/Background_*.glb`, picked up automatically; thumbnails are cut from the texture inside each `.glb`). A click stands that backdrop still at the back edge of the stage floor, scaled to the floor's (`Ground_Box`) width and unlit, (`src/stage/backdrops.ts`), replacing the previous one; a second click removes it. Backdrops are revealed like a sheet let down from the fly loft: they sink into place while a ragged torn-paper edge uncovers them from the top (shader discard on uv), and hide in reverse; switching crossfades.
- **Requisiten** (props, `src/props/requisits.ts`): the same slider, mirrored on the left (`createSlider({ mirror: true })`), lists every `.glb` in `assets/digital.skkg.ch/requisits/`. Card picture: an image with the same name next to the `.glb` (`Stuhl.png`) if there is one, otherwise the model is rendered once in a small offscreen renderer. A click lowers the prop onto the stage as if on a string (kinematic), a second click lifts it off. The spot is chosen by best-candidate sampling: of 24 random spots on the floor the one with the most room to the props already there wins, so props spread out. Standing props are dynamic Rapier bodies (box collider; small ones register as grabbable); they are dragged across the floor with mouse or finger (kinematic while dragged, pushing others aside; the orbit camera is held off by a capture-phase listener). A prop knocked off the stage is let down again on a free spot. Anything larger than 0.5 m is scaled down.
- **IIIF objects** (`src/props/iiif.ts`): the last props card is a drop field. A IIIF 3D manifest (Presentation 4, e.g. `IIIFManifests/microscope_ethz_GEOB_0055.json`) dropped onto the slider as a file or link (a viewer link with `?manifest=` works too), or picked by a click, becomes a new prop card and lands on the stage at once. Read from the manifest: label (shortened to its first part), thumbnail, homepage (the card's "i") and the first painted `Model` with its rotate/scale transforms; the scene's cameras and lights are ignored. The `.glb` is loaded from where the manifest points (it must allow CORS), at real size in metres; Draco is decoded with three's decoder, served under `/draco/` by the Vite plugin. Added objects last until the page reloads.
- **Plays and scene presets** (`src/plays/`): a play ("Stück") is a list of scenes, each a stage preset: backdrop, props with their spots, and its light: `light: { "scene": "<id>" }` names a lighting scene of the shared library (`assets/lights/`, see Lighting scenes), with the desk's `values` next to it if the sliders were changed without saving them as a lighting scene. A scene without `light` is lit with Neutral, so its light does not depend on the scene shown before. A `sound` field is reserved for the Sound page (kept when a scene is saved again, not applied yet). One JSON file per play in `assets/plays/<id>.json` (id = file name; a sign's play, e.g. `froschkoenig`, picks up the file of the same name). Prop spots are relative to the floor (`x` 0 left … 1 right, `z` 0 back … 1 front, `yaw` in degrees), so presets survive a rescaled stage. The files are fetched at runtime, not imported, so saving does not reload the page: the `plays` plugin in `vite.config.ts` lists, serves and (dev server only) writes them, and copies them to `dist/plays/` in a build.
  - **Director bar** ("Regie", `src/plays/director.ts`), a paper strip at the top in impro mode: pick a play or create one (asks for its name), **+ Szene** starts a named scene from the stage as it stands, the impro panels set it up, **Speichern** stores the stage in the chosen scene and writes the file (a build downloads it instead). A click on a scene puts it on the stage, a double click renames it, × deletes it. **Download** saves the play as `<id>.json` (with the scenes as they are in the bar), to keep a copy or swap it into `assets/plays/` by hand; **Laden**, or dropping such a file onto the bar, brings it back in place of the play with the same id (a browser's `froschkoenig (1).json` counts as `froschkoenig`) until **Speichern** writes it.
  - **Scene buttons** (`src/plays/scene-buttons.ts`): when a play with scenes is chosen (the Froschkönig sign; `?test=nocurtain&play=froschkoenig` skips the curtain), the first scene stands on the stage once the main curtain is up, and golden numbered medallions with the scene names down the left edge, or the number keys 1–9 (not while typing in a field), switch scenes: the stage curtain comes down, the set changes behind it (backdrop crossfade, props lifted off, moved or lowered by `arrangeRequisits`), and it goes up again.
  - **The puppet steps aside** while a scene preset is put on the stage (`applyScene`, so also for the director bar's scenes, `hidePuppets` / `showPuppets` in `src/puppet/puppet.ts`): it fades out with its strings, cross and follow spot, the cross is pulled 1 m up out of the way, and only then do the props come down; once all have landed it is let down again and fades in.
- **Back to the play choice** (`src/plays/play-menu.ts`): a round **Stücke** button at the bottom left (the sound button's style) whenever the main curtain is up. The main curtain comes down, behind it the play's UI goes (impro panels and director bar are hidden and shown again on the next impro, the scene buttons removed), backdrop and props are cleared, the music goes back to the curtain's, and the signs drop in again. Unsaved changes in the director bar are asked about first. With `?test=nocurtain` curtain and signs are loaded only at that moment.
- **Catalogue** (`assets/catalogue.json`, read by `src/catalogue.ts`): hand-edited per file name, for props (`requisits`) label, `scale` and `source`, for backdrops label and `source`. A scale other than 1 shows under the card's name as "Massstab 1 : 5". `source` is the object's page in the SKKG collection: a round gold "i" on the card's outer side (left on props, right on backdrops) opens it in a new tab. `"ai"` marks an object invented without an SKKG original: the "i" then shows the "Fake-Objekt gefunden!" popup (beige paper with the slider's scalloped gold edge, `src/impro/source-info.ts`). An empty `source` shows no "i".
- A central stage that fills the room: proscenium, curtains, and layered paper-theatre backdrops (scans as alpha planes).
- Behind the theatre: a curved red velvet wall with a gold band at its foot (`assets/stage_parts/wall.glb`, `src/stage/wall.ts`), 4 m wide, its hollow side towards the camera, 0.3 m behind the stage; the velvet texture is grey and tiled (one repeat per 0.5 m) instead of stretched; its colour is multiplied in from `VELVET_COLOR`.
- Around the theatre: a 20 m ground plane with the tiled asphalt wood (`assets/textures/herringbone_parquet_diff_1k.jpg`, one repeat per 1.5 m) at the bottom of the stage model, fading out radially so there is no horizon line (`src/stage/ground.ts`).
- **Stage lighting** (`src/stage/lighting.ts`, `LightingSystem`): the rig a theatre lighting designer set up for us, five groups, each on a dimmer (0 … 100 %):
  - **Front light** (Vorderlicht): two white lights out front, 45° up and 45° to either side, diffuse over the full stage width, 3000 … 5600 K (directional lights).
  - **Profile spot** (Profilscheinwerfer): the follow spots below; nearly parallel, hard light with a soft rim. Brightness, colour temperature, beam angle, softness of the rim, haze.
  - **Top light** (Oberlicht): an area light above the stage, any colour: the mood. 40 % in the plain scene.
  - **Side light** (Seitenlicht): area lights in the wings on both sides, for plasticity; 3000 … 5600 K.
  - **Striplight** (Rampe): along the front edge of the floor, shining up at 45° into the faces, any colour.
  - Top, side and strip are `RectAreaLight`s: soft, without a visible source (no "wall of light"), falling off with distance, so they light the stage and not the room. Only the profile spots cast shadows.
  - A sixth dimmer, room light, sets the environment reflections on the glossy materials.
  - The renderer has no tone mapping (the unlit painted parts keep their colours), so light adds up to white; the scenes are balanced so that light clothes do not burn out.
  - The painted backdrops are unlit: they are tinted with the light that would fall on a sheet at the back of the stage, worked out from the dimmers (mostly the front light). The proscenium, also unlit, keeps its colours.
- **Lighting scenes:** a lighting scene is one set of values for the rig, with a name. They form a library shared by all plays: one JSON file per scene in `assets/lights/<id>.json` (`name` and `values`, colours as `"#rrggbb"`; a missing value is taken from Neutral). **Neutral** (the start) is built in; **Morgenstimmung**, **Abenddämmerung** and **Dramatisch** come as files. Switching fades over 1.5 s; lights are never added or removed (that would recompile every lit material).
  - The files are fetched at runtime as one list (`lights/index.json`, the `lights` plugin in `vite.config.ts`), not imported, so saving does not reload the page. The dev server writes and deletes them; a build has `dist/lights/index.json`, keeps a saved scene in the browser (`localStorage`) and downloads it as `<id>.json`, to be put into `assets/lights/` by hand.
  - **Light desk** (Lichtpult, `src/ui/light-desk.ts`): the lighting scenes as buttons, one slider or colour field per parameter, grouped by light, and **Lichtszene speichern**: with a name it adds a lighting scene every play's scene can use, without one it overwrites the chosen scene, which changes it in every scene that uses it. It is the **Licht** page of the scene editor (impro mode) and, for the other pages, a button in the debug panel.
  - A play's scene gets its light like its backdrop: set it on the Licht page, then **Speichern** in the director bar. Putting a scene on the stage (director bar, scene buttons) fades to its light; going back to the play choice goes back to Neutral.
  - **Licht: …** in the debug panel, or the L key (also outside debug mode), steps through the scenes; `?light=<id>` (`morgenstimmung`, `abenddaemmerung`, `dramatisch`, or any other file name) starts in one.
- **Follow spots** (`src/stage/spotlights.ts`, `SpotlightSystem`): every puppet on the stage gets its own profile spot, created with the puppet (`createPuppet`), which tracks its chest with a slight lag.
  - They hang on a lighting bar out in front of the stage (1.6 m in front, 1.2 m up, above the camera's view), as front-of-house spots do in a real theatre, each as a small fixture that turns with its beam.
  - They add a pool of focus light around the puppet to the stage already lit by the other groups; the beam is also drawn as faint haze (an additive cone, rendering only). Their look comes from the lighting scene.
  - They are the only lights casting shadows; on phones only the first spot does.
- The marionette and props it can interact with: hold, throw, drop.
- **Exit** goes back to the title.

**UI/UX, "game theatre" character**
- Curtain transitions, ticket- or programme-style buttons, Geist Sans for the UI, Geist Serif for titles.
- **Debug mode** (`src/ui/debug-mode.ts`): the test links top right, the debug panel at the bottom, and the HUD (landmarks, FPS, physics wireframe) are hidden by default; the camera preview with the hand landmarks always stays visible, as the player's feedback. Shift+D toggles them, `?debug` switches them on; the state is kept in `sessionStorage`, so it survives the test links' reloads within the tab.
- **Sound** (`src/audio/`, `src/ui/sound-toggle.ts`): two round buttons at the bottom right, below the camera preview: **effects** in the corner (speaker: excerpts, cues, physics sounds) and **music** left of it (note: the background playlists). Both are **off at every page load** (not remembered); the first sign click turns both on (a later choice through the **Stücke** button keeps what the visitor set), a Sound page card the effects. The first click creates the `AudioContext` (the user gesture iOS needs). Left of the buttons, while music or an excerpt plays, the credit of the track (title · creator · licence), linked to its archive.org item, as the CC BY licences require. Background music is streamed from archive.org, never committed (the NC/ND licences allow playing, not cutting): `assets/sounds/archive.json` lists the playlists and which play uses which (`ragtime` by default and for the curtain, Froschkönig `frogs`, Hänsel and Impro `percussion`; the Kaleidoscope EP was dropped, it has no licence); a sign click crossfades to the play's playlist. Its tracks and credits are written by `scripts/index-archive.mjs` from the archive.org metadata API; items without a licence are left out, and an empty playlist falls back to `ragtime`. The audio elements go through Web Audio (archive.org sends CORS headers), because iOS ignores `HTMLMediaElement.volume`.
- **Excerpts** (`src/audio/excerpts.ts`): passages of Oda Klonk's "Ein Haus das klingt" (start and end in `archive.json`), played from the stream by seeking (archive.org serves range requests) and faded out at the end, never cut into files (ND licence). The impro **Sound** page lists them as cards (`src/impro/sound-icons.ts` draws their pictures); a click plays one and turns the effects on if they were off, a second click stops it, the "i" opens the archive.org item. While an excerpt plays, the background music ducks to 30 % and the credit line shows the excerpt. Event cues (`archive.json` "cues"): the sign click plays "Eröffnung" (the end of the drum roll into the announcement "So meine Damen und Herren …") while the curtain rises.
- **Effects** (`src/audio/sfx.ts`, `cues.ts`, `impacts.ts`): CC0 samples from two packs committed as zips in `assets/sounds/opengameart.org/` (Kenney "50 RPG sound effects", rubberduck "75 CC0 breaking, falling and hit SFX"); `scripts/unpack-sounds.sh` (POSIX sh, needs unzip) copies the ones used into `assets/sounds/sfx/` (git-ignored) under fixed names; it runs by itself before `npm run dev`, `dev:https` and `build` (`npm run sounds`; without `sh` or `unzip` it only warns, and only ZzFX plays), grouped by the name before the number, a random variant per play. Small synthetic sounds come from **ZzFX** (`zzfx` npm package), rendered into our own audio graph; a group without decodable samples falls back to it where one is given. Cues: a sign knocks when it reaches its place (each time a row drops in), a prop's rope creaks when it is lowered or lifted and it thuds on landing, a backdrop rustles like paper. **Physics:** Rapier collision events (switched on for the puppet parts and props) at contact start; the relative speed sets sound and volume, the collision group what was hit (puppet: wood, pitched up for the small puppet, ZzFX ticks for soft contacts; props: set down or falling); a speed threshold, a cooldown per pair and at most 4 sounds per 100 ms keep a resting puppet quiet. Panning is stereo across the stage (no positional audio at this scale). Contact force events were dropped: they fire every step while the puppet stands on the floor.
- An old-film vignette (darkened, softly burnt-in edges) lies over the 3D view in 2D, under the UI (buttons, HUD, impro menu and slider): a CSS overlay in `index.html` that lets all input through.
- Without `?test` the page is the play itself: curtain, signs, then the marionette with hand control. Debug buttons top right (debug mode, Shift+D) pick `?test=…`; **impro** (`?test=nocurtain`) skips the main curtain and the signs and goes straight into impro mode; **puppet** is the marionette with the mouse only, **world** the stage alone with an orbit camera.

## 3. Marionette control

### 3.1 One input model

```ts
interface ControlInput {                              // mutable, written once per frame
  bar: { position: Vector3; rotation: Quaternion };   // main bar of the control cross (Spielkreuz), rig coordinates (the engine adds stringExtra)
  rock: { hands: number; legs: number; head: number }; // rad: rocking the hand bar (±0.6), the leg bar (±50°) and the head bar (±45°)
  nod: number;                                        // 0…1: the head goes forward (the puppet looks down)
  turn: number;                                       // −1…1: the head turns about the vertical, + to the puppet's left
  handBar: { detached: boolean; position: Vector3; rotation: Quaternion }; // the hand bar taken off the cross: its own world pose
  hook: { id: StringId | null; along: number; offset: Vector3 }; // a string caught by the other hand: where along it (0 eye … 1 socket) and how far it is pushed off its line
  stringExtra: number;                                // m: strings this much longer than in the rig, the cross that much higher (a player's setting)
  pulls: Record<StringId, number>;                    // 0..1 per string on top (plucking): head.L/R, shoulder.L/R, back, hand.L/R, knee.L/R
  grip: { left: boolean; right: boolean };            // a level: the magnet in this puppet hand is on (it takes the prop in reach); off does not let go
  release: { left: number; right: number };           // counters: each change lets go of what this hand holds
  source: "mediapipe" | "phone" | "mouse" | "remote-phone" | "xr-3dof" | "xr-6dof";
}
// The other way, engine → sources and UI, written in every physics step (puppet/grab.ts): the prop each hand holds, and the one its magnet would take now
const puppetState: { holding: { left: string | null; right: string | null }; inReach: { left: string | null; right: string | null } };
```

`grip` is a level and `release` a counter, not pulses: the camera runs at about 30 Hz and the physics at 60 Hz, so a pulse of one frame is missed or seen twice.

| Source | Bar pose | Rock (legs / head / hands) | Hand bar off the cross | Pulls | Grip | When |
|---|---|---|---|---|---|---|
| MediaPipe (webcam on desktop or phone) | Palm of the cross hand: position, height in metres, size (depth) and tilt | Index against middle finger of the cross hand (legs); thumb and little finger turn the head (`turn`); a second hand can take the leg bar or the head bar at its handle and turn it | A second hand takes it and rocks it by turning the fist | None; a second hand pushes the back string (`hook`) | The second hand's fist away from the rings; a quick fist/open lets go | now |
| Phone sensors + touch | DeviceOrientation (3DoF) | Open (not decided; e.g. touch sliders) | Open | Touch zones/sliders | Button | now |
| Mouse/keyboard | Drag, wheel | Q/E legs, A/D hands, Y/X head, T nods the head, U/I turn it, sliders | H, then pointer and wheel | Sliders; B pushes the back string | F / G held, a tap lets go | now (dev) |
| Another device in the room (WebRTC, section 3.3) | Any of the above, on that device; its whole `ControlInput` is sent to the host | Same | Same | Same | Same | now |
| WebXR 3DoF / 6DoF | Controller orientation / controller or `XRHand` pose | Open (not decided) | Open | Trigger / finger joints | Grip / pinch | later |

#### MediaPipe hands

MediaPipe (`HandLandmarker`, two hands) runs with `detectForVideo` on `requestVideoFrameCallback`, separate from the render loop. It uses the GPU delegate and falls back to CPU. The wasm and the `.task` models are served locally from `/mediapipe/`, so no CDN is needed at runtime.

**Start.** The click on a sign starts the camera (`startHandTracking()`, the user gesture iOS needs; the stream is requested before anything is awaited, the model loads during the permission prompt), possibly before the puppet has loaded; `setupHandTracking()` connects the puppet once it is there and adds the camera button (or C) for `?test=nocurtain` and a second try. `@mediapipe/tasks-vision` is loaded only then.

The code is split so that everything but the camera runs without a browser:
- `src/input/hand-tracking.ts`: pure functions and the `HandTracker` state machine (landmarks in, plain numbers out). Its `MAPPING` and `TUNING` tables hold every number that shapes the feel.
- `src/input/mediapipe.ts`: camera, landmarker, writing `ControlInput`, recording and replay.
- `src/input/hand-overlay.ts`: the picture above the camera feed.
- `src/input/hand-synthetic.ts`: a synthetic hand for tests and for `?replay=synthetic`.
- `src/input/body-frame.ts`: the hand's height (`BodyFrame`: pure, no import of the tracker, which reads it), and the types of what the body models see. `src/input/scene-synthetic.ts`: a camera, a hand and a player in a room, in metres, projected to landmarks and body observations, for its tests (the synthetic hand is posed in the picture, which cannot say "the same hand, seen by a camera 30 cm lower and pitched up").

**Hand roles.** The first hand seen is the cross hand and stays it; a second hand can take the hand bar, the head bar or the leg bar, push the back string, or switch on the magnets in the puppet's hands with a fist away from the bars' handles. MediaPipe has no persistent ids and its result order changes, so each detection goes to the role whose palm was last seen nearest, with the handedness label as a tie-breaker. A hand that vanishes keeps its outputs for 0.5 s; after 1.5 s the cross hand gives up its role, and a remaining second hand moves up (the only hand in view is always the cross hand). The first two results after a hand is (re)detected are thrown away: they come from the rough palm-detector box and are far off. Whether a hand that takes the cross is a new player (`TrackerOutput.player` goes up) is decided by the height model (`BodyFrame.handAppeared`), so that a replay reproduces it, and in the first frame in which the hand counts (its first results are thrown away, so it has no size before): the same player if the hand was gone for less than 5 s and comes back with a palm within 30 % of the size it left with; where a face or a body is in use, if that stayed in view through the gap instead (never missing for more than 1 s, its size within 25 %). Otherwise a new player, who starts without a zero for the height and is offered its capture; what is known about the camera stays. A detection that never counted (a ghost) is no hand that came and went. (Until then: any hand after 5 s without one.)

**Mapping** (tilt, depth and fingers are relative to the hand's rest pose, see below; the "Kreuz zurücksetzen" button or N takes a new one):

| Hand motion | Input |
|---|---|
| Palm centre in the image, sideways | `bar.position` x (the inner 80 % of the image spans the stage) |
| Hand higher / lower than the height at which the puppet stands (where the player first held the hand still, see "Height in metres") | `bar.position` y, from the cross's rest height: nothing within 3 cm of the standing height (up to 6 cm while that height is not sure), then 1 m of cross per m of hand, at most 0.25 m down (the strings go slack, the puppet sinks) and 0.4 m up (it is lifted) |
| Hand comes closer to the camera / goes away from it | `bar.position` z: to the front of the stage / upstage |
| Tilting the hand forward / back, sideways, turning it | `bar.rotation`: pitch about x, roll about z, yaw about y |
| Index against middle finger, bent down at the knuckle ("walking fingers") | `rock.legs` |
| Thumb pressed in / little finger bent down | `turn`: the head turns left / right, to the side of the pressed finger as the player sees it |
| Second hand makes a fist away from the bars' handles | `grip` left and right while the fist stays closed: the magnets in the puppet's hands are on, and a free hand takes the prop in its reach. Opening the hand switches them off; what a hand holds stays in it |
| Second hand makes a quick fist/open (open again within 0.6 s) while the puppet holds something | `release` left and right go up by one: the puppet lets go. A fist that stays closed longer is the magnet again |
| Second hand pinches or closes at the hand bar's handle | `handBar.detached`; the bar then follows that hand (position, depth) from where it was taken, and rocks as the fist turns (one puppet hand up, the other down) |
| Second hand pinches or closes at the head bar's handle and turns | `turn` while it holds (the fist's top to the right: the head to the right); let go, the cross hand's fingers have the head again |
| Second hand pinches or closes at the leg bar's handle and turns | `rock.legs` while it holds, in place of the walking fingers (large or held steps); let go, the fingers have it again |
| Second hand, open, moves sideways against the back string | `hook` on the back string: pushed along with the hand's leading edge (up to 12 cm), let go when the hand draws back. On the stage the string is drawn back (upstage) by that much and only 30 % sideways: the camera cannot see depth, and drawn back the puppet bows instead of swinging round |

The leg bar is rocked by the difference of two finger angles, so moving or turning the hand does not trigger it, and it fades out while all four fingers close. The bar end on the side of the bent finger goes up. An index bent 30° further than the middle finger is a full rock; for the middle finger 18° are enough, because bent on its own it does not go far (on the recorded session it read 0.2…0.55 rad where the index read 0.5…1.0, so with one gain for both its leg rarely made a full step). The head is not tilted or nodded by a finger: it tilts and nods with the cross, and thumb and little finger turn it.

**Thumb and little finger turn the head.** On the real cross the small head bar (the sub-cross) is turned on its post and rubber strings take the head along. Here the two outer fingers of the cross hand do it, like the two outer keys of the hand: thumb pressed in turns the head to the thumb's side of the picture, little finger bent down to the other (`ControlInput.turn`, −1…1; for either hand and with the picture mirrored or not). The thumb's measure is how far its tip has left the place in the palm it had at the rest pose (the part that goes outwards, a thumb spread further, does not count): nothing below 0.25 palm lengths, a full turn at 0.55 (on the recorded session it read up to 0.22 while the other fingers stepped and the hand tilted, 0.4…0.6 tucked in). The little finger's is its bend angle less 0.6 times the middle finger's, between 0.15 and 0.5 rad: it goes along with the middle finger (on that session it read 0.2…0.36 rad when only the middle finger stepped). The turn fades out with a fist and at edge-on leans like the leg bar. On the recorded session, which has the first mapping's thumb and ring / little-finger gestures in its last 15 s, the turn is exactly 0 for the 44 s before, steps included, and answers to those gestures. Until the third play test a pinch (thumb tip to index tip) brought the head forward instead (`ControlInput.nod`, still in the engine for the keyboard): the thumb cannot serve two gestures without cross-talk, and turning was asked for. Not tried on a real hand.

**The hand is the cross (decided).** The cross lies in the palm: a palm held level is a level cross, the fingers work the bars. A puppeteer keeps the wrist in line with the forearm, so the palm's tilt is the arm's tilt, and the arm and shoulder set height and place; tracking the palm therefore covers what the arm does. Tracking the elbow itself (a pose model) is open.

**The player's view (decided).** The webcam faces the player, who stands or sits in front of the screen. The hand moves the cross the way the player sees their own hand move: right is right, up is up, and the cross turns and rolls as the hand does. Coming closer to the camera brings the puppet to the front of the stage, going away sends it upstage: a player who walks towards the screen sees the puppet come towards them. (Until the second play test it was the other way round, hand towards the screen = upstage, as if the hand pushed the puppet away; walking up to the camera then sent the puppet to the back.) Tipping the hand forward (fingertips down) tips the front of the cross down, so the puppet bows towards the audience: for pitch the hand is the cross, fingers at its front, although the puppet faces the player (`TUNING.tipForwardBows`; off, the cross tips as the hand is seen to tip, far end down). The camera sees all of that from the front, so the picture is mirrored (`HandTracker.mirror`, on by default). `?mirror=0` or M turns it off, for a camera on the player's own side (a phone's back camera, never mirrored) or a player behind the stage: sideways and the turns are the other way round then, depth is the same. MediaPipe always gets the raw image; on it, its handedness label is the player's real hand (checked on MediaPipe's own test photos with tasks-vision 1.2).

**Palm size and orientation from the image (decided).** Both come from the outline of the rigid palm (wrist and four knuckles) in the image, not from MediaPipe's 3D "world" landmarks. The palm is a flat shape of known proportions; seen at a slant it is squeezed along one direction and keeps its size along the other. So the least-squares map from that shape to the image gives the size (its larger stretch) whatever the slant, and the lean (the ratio of its two stretches is the cosine). Why not the 3D landmarks: on a real recorded session they shrank by a third whenever the hand was seen at a slant, which threw the puppet to the front of the stage on every bow, and they flipped between "leaning forward" and "leaning back", which made the tilt move in steps. What the outline cannot tell is which way the palm leans. A hand that holds a cross leans its fingers towards the screen, so that is assumed; the 3D landmarks only decide while the fingers do not clearly lean, and they give the whole orientation while the palm is nearly flat to the camera (there the outline hardly changes with the lean). The tilt against the rest pose is a rotation vector, not Euler angles, which locked up when the hand pitched towards 90°. A level palm is close to edge-on to the camera and may tip through it; the shape's handedness is fixed when the hand is first seen, so the orientation carries on to the other side. Known limit: a hand leaning *away* from the camera by more than about 25° is read as leaning towards it.

**Fingers as angles (decided).** A puppeteer's fingers work the bars like piano keys, so a finger's signal is the angle by which it is bent down out of the palm at its knuckle. The finger is taken as a stick from knuckle to tip that turns from where it lies at rest towards the palm side; the palm's orientation says where such a stick appears in the image for every angle, and the angle whose stick fits the finger as seen is taken. The finger's length and the direction it fans out in are measured on the player's own hand at the rest pose. Why: the first version mapped each fingertip back through the palm's outline, which only holds for points in the palm's plane. On the recorded session the same bent index finger read as fully curled with the palm leaning 0.75 rad, as a third of that at 1.1 rad, and the rockers were faded out from 1.2 rad on, which is where a level palm is: the leg bar was an on/off switch in one pose and dead in another. With angles the same session gives a full rock for the same bend at 0.75 and 1.2 rad, graded in between, and no rocking while the fingers rest (leg bar within 7 % of its range). The outline map is still used for the thumb (how far its tip sticks out beyond the index knuckle), the pinch and the fist; a fist also needs the 3D landmarks to agree (an edge-on hand looks like one in the image), and above a lean of 1.2 rad a fist is not read at all (a closure that has begun goes on: it ends when the hand is seen open). Limits: the rockers fade out only above about 1.4 rad (the palm is a line there); seen flat-on (an open palm shown to the camera), a finger bending towards the camera hardly changes in the image, so below a lean of 0.3…0.6 rad the angle is taken from MediaPipe's 3D landmarks instead (how far the finger rises out of the palm's plane; flat-on is where those landmarks are at their best), filtered harder, with a dead zone of 0.1 rad (the first version kept the image there with a dead zone of 0.25 rad, and walking fingers were not read unless bent a long way; on synthetic hands the same bend now steps alike at an open palm, at 45° and at a level palm, also when the rest pose was taken at another angle; not tried on a real hand, the recorded session has no open palm); a hand seen from the back is read too, but only up to the angle at which the bent finger lies in the image plane (not tried on a real hand).

**Depth without a distance sensor.** The palm's size in the image is ∝ 1 / distance. The puppet's z is the log of that size against the size at the rest pose (0.75 m of stage per unit: a third closer is 0.2 m to the front). It stays where the hand is: a player who walks up to the camera and stays keeps the puppet at the front. (The first version measured against the median of the last 10 s, so a hand held forward drifted back to the middle; that suited a seated player shifting on a chair, not one who walks.) The reset button takes the hand's present distance as the middle of the stage's depth. The measure is trusted less while the hand moves fast across the image (MediaPipe's box lags and reads a few percent too large). Tipping the hand forward still moves the puppet a little, because the knuckles really come closer to the camera. Distance from the head or body (a second model) is open.

**Height in metres (decided).** The cross follows how far the hand is above the height at which the puppet just stands, in metres: at that height the cross is at its rest height; lower, the strings go slack and the puppet sinks down; higher, they lift it. That reading (`TrackerOutput.height`: the model `BodyFrame` in `src/input/body-frame.ts`, every number in its `HEIGHT` table) does not depend on where the camera is or how it is pitched, once the camera's horizon row is known, and its zero is where the player holds the hand, not a height above the floor. Before, the hand's height was (0.5 − y) · 0.095 / s above a camera taken to be level and 1 m above the floor, with a slider for the standing height: re-projected as from a camera pitched by ±15°, the recorded session read 15.5 cm off and wandered over 8 to 9 cm as the hand changed its distance.

- **The model.** A palm P = 9.5 cm long that measures s image heights gives m = P / s metres per image height at the hand. With y_h the horizon row (the row of the picture at the camera's own height: 0.5 for a level camera, 0.5 + f · tan θ for one pitched up by θ) the hand is H = c · (y_h − row) · m above the camera's horizontal plane, c = cos θ. That is exact for any pitch; the old reading is the case y_h = 0.5. The cross gets `value = H − H0 − b − trim`: H0 the zero, b the body shift (anchors, below), trim the player's slider. Of the camera only y_h is needed, and for the zero not even the focal length: c is taken from y_h with an assumed focal length of 1.1 image heights, which is off by at most 3 % of H for webcams (0.9 … 1.5) at 15°. Palms differ by ±15 %, which scales travel by as much and leaves the zero where it is.
- **The zero: a guided capture.** A new player sets it by holding the hand still where the puppet is to stand. The puppet answers from the first frame (with the zero the ladder below gives), and the hand window shows a band of rows in which a zero is taken: rows 0.35 … 0.70 of the picture, where the hand is seen well and has room both ways. One hint at a time: "Bitte einen Schritt zurück" (palm longer than 0.25 image heights), "Hand etwas höher" / "Hand etwas tiefer" (outside the band), "Fingerspitzen leicht zur Kamera neigen" (palm leaning more than 1.2 rad from flat: seen edge-on), and when all is good "Ruhig halten …" with a bar that fills in 1 s (the rest pose's own time). Then "So steht die Puppe" for 1.5 s while the band closes onto the standing line. The zero is the average over the hold, kept as the row and scale of that moment (not as metres), so that a horizon row learnt later moves it along and the reading at that distance stays 0. The capture is offered for 8 s, which only run while the hand leads the puppet and the puppet has landed (see "Connecting and letting go"). Not taken in that time, the zero stays what it was and is not taken behind the player's back later; "Kreuz zurücksetzen" takes it at any time, wherever the hand is.
- **The horizon row**, by how far it is trusted: (1) measured by whoever sets the camera up: "Kamera einmessen" in the debug panel asks for the hand laid at one fixed height (a table's edge, a stick), held still near the camera and then further away. At the horizon row a hand at the camera's height stays put whatever its distance, so two holds give it (`horizonFromTwoHolds`: (y_h − row_a) / s_a = (y_h − row_b) / s_b); further holds are averaged in (a line through all, `HorizonHolds`). It is in use at once and remembered in the browser for that camera and picture size (`hand-horizon`; another resolution is often another crop); "Einmessung löschen" forgets it; `?horizon=<row>` wins over it and is not stored. (2) Fitted from a face or body that walks towards the camera (`HorizonFit`: its row is a straight line in its size, whose value at size 0 is the horizon row; given only once the sizes spread by 1.5 times; kept for the page session). Needs a body model, so not in play yet. (3) Not known: 0.5, a level camera. While a hand plays, the row in use moves by at most 0.05 rows per second.
- **Anchors: a face or a body (read by the model, not run in play).** `BodyFrame.update(hand, body?)` takes a `BodyObservation`, which exists only while recording and in the replay of such a recording. An anchor is a second height measured the same way with its own ruler: the eyes' row and distance (0.063 m; the way from the eyes to the mouth takes over once it is clearly the larger, for a turned head; the two are averaged before they are compared, because the larger of two noisy measures is too large), or the shoulders' row and width (0.36 m). Which face: the one that continues the last, else the one above the hand, at a plausible distance behind it and nearest to its side; detections with a score under 0.7 or an impossible size are left out (the detector reported faces on a test pattern); which body: the one whose wrist is at the hand. An anchor counts after 0.4 s and four sightings, and its row and size are low-passed (0.5 s). It gives three things. A first zero before any capture: the hand is taken to play 0.42 m below the eyes or 0.22 m below the shoulders, which are assumptions, not measurements. The body shift b: with the horizon row known, the zero follows the anchor only when it has changed by more than 8 cm (and more than three times what its ruler is good for) for 1 s (sitting down, standing up), at 0.3 m/s at most, and nods and the bob of walking are left alone; with the horizon row unknown it follows every change, because a walk towards a pitched camera lifts the anchor's reading as it lifts the hand's, and following cancels that. The shift is kept as two levels (row and scale), not as metres, so that what was followed under a wrong row comes out right once the row is known, and a shift under the threshold is let go. An anchor not seen for 0.6 s freezes the shift; back, it is counted anew, not applied. And the horizon fit above.
- **How sure.** The reading carries `sigma`, how far its zero may be off (a slow error, not frame noise): 0.5 cm for a taken zero, 6 cm for one guessed from an anchor, 15 cm for none, plus what the horizon row's own error makes of the distance walked since the zero was taken ((m − m0) · σ_h, with σ_h = 0.01 rows measured, 0.15 unknown), 1.5 % of H for the palm's size (more for a fast or small hand) and 2 cm while an anchor is followed. `confidence` is 1 − sigma / 10 cm. The standing band (`TUNING.position.dead`, ±3 cm) is wider by sigma, up to ±6 cm: before the zero is taken the puppet stands for a hand that is only roughly right. `sources` says what the reading rests on; the hand window shows it.
- **The ladder**, best first: zero taken and horizon row measured (right at any distance and pitch) → zero guessed from an anchor (not in play yet) → zero taken, horizon row unknown (right where it was taken; a pitched camera lets it drift with the hand's distance, and sigma grows to say so) → nothing: the old reading, a level camera with the puppet standing for a hand at the camera's height.
- **No jumps.** A change of the zero (capture, a guess appearing, the slider, a shift let go) comes in over 0.5 s and no faster than 0.3 m/s; sigma follows over 0.4 s. After a reset the tracker moves the whole cross over within its 0.6 s, and the height model does not ease on top.
- **The size the height is taken with** goes through the very filter the palm's row goes through (the same share of each new frame, `Track.heightPalm`), not through the slow one of the depth. A hand that keeps its height while the player walks towards the camera moves in the picture in proportion to its size, and only if both lag alike does their product stay put: with the slow size (which is taken with less weight while the hand moves in the picture, as it does all through such a walk) the walk read up to 7 cm of false lift for a hand 20 cm above the camera's height. The price: a hand racing sideways may read a few percent too large for a moment, which is that share of H.
- **Where to put the camera** (for the hints, and for whoever sets up): the hand tracks best with the palm seen at a lean of 0.6 … 1.1 rad from flat (a level palm seen head-on shows only fingertips), so the camera goes 15 … 25 cm below the standing hand and 0.7 … 1.2 m in front of it, pitched so that the hand sits in the middle third of the picture. The cross's pitch zero is unchanged by all this (rest pose and "Kreuz neigen").

Standing is a band, not a line: within 3 cm of the standing height the cross stays at its rest height (`TUNING.position.dead`), because a hand cannot hold its height to the centimetre the legs need (on the recorded session it wandered by 2 cm while the fingers stepped; the knee strings are slack 1 cm below the standing height, which the engine's take-up makes up for). Lifting and sinking start at the band's edges, without a step.

What was measured (`scripts/test-body-frame.ts`, and the recorded session through `replay-recording.mjs`):
- Synthetic scenes, hand only. Horizon row given, cameras pitched −15° / 0° / +15°, at 0.6 / 1.0 / 1.8 m: the hand's height above the camera's is right within 0.34 cm (focal 0.9), 0.76 cm (1.2) and 1.26 cm (1.5; the target was 1 cm), a 10 cm lift reads within 0.28 / 0.45 / 0.66 cm (target 0.5): at focal 1.5 the assumed 1.1 costs 2.8 % in cos θ, on top of about 2.5 % that remain at 0.6 m with the right focal length (probably the palm's own depth: the knuckles, which set its size, are nearer the camera than its centre). The capture: taken after 1 s in the band, on the frame the rest pose is; not taken outside the band, edge-on, too close, while the puppet flies or the hand is not connected, or after 8 s; a zero up to 3 cm away comes in at 3 mm per frame at most, a larger one at 0.3 m/s (10 mm per frame at 30 Hz).

**Rest pose.** In the hand's rest pose the cross hangs level, the puppet is in the middle of the stage's depth, and the leg bar and the head are at rest. The cross answers from the first frame: until the hand has paused, a usual pose stands in (a palm held level in front of the screen as a webcam below it sees it, leaning 0.9 rad from flat to the camera; measured on the recorded session). The first time the hand holds still for 1 s, its own pose becomes the rest pose (orientation, distance, and how its fingers and thumb lie) and the cross eases over (0.5 s). The leg bar and the head's turn wait for that: finger lengths and how a relaxed thumb lies differ from hand to hand, so the stand-in has no zero for them. The overlay asks for the pause. "Still" is measured in palm lengths per second, not in image heights: a hand three times further away moves a third as fast across the picture, counted as still all the time, and had its rest pose taken in the middle of a bow (the recorded session replayed at a third of its size: the cross then sat 0.55 rad off in pitch for the rest of the session; with the fix and 1 px of noise it differs from the original by 0.03 rad rms). Tried and dropped: waiting for the pause before tilting at all (the player on the recorded session moved for 11 s first), and taking the pose on a timer (it caught the hand on its way into a bow). With the guided capture of the standing height (see "Height in metres") the two are taken together: when the capture takes the zero, the hand's pose of that moment becomes the rest pose (again, if a first pause had taken one already, as it does while a new player's puppet is still flying in), so that where the puppet stands the cross is level and in the middle of the stage's depth. A hand that is in the band and still from its first frame gets both on the same frame. The overlay's own request for a pause shows only while no capture is offered.

**Reset ("Kreuz zurücksetzen", N).** Sets the cross right: the hand as it is held now becomes the rest pose, and everything decided about the hand from earlier frames is dropped (which way round its outline runs, which way it leans, its handedness label, the finger calibration, every average), in case one of those is what tilted the cross; before, such an error stayed until the hand had left the picture. The cross waits where it is for 0.4 s (the averages have to fill again), then goes level within 0.6 s, without a jump. It also takes the hand's present height as the height at which the puppet stands (`BodyFrame.capture`), wherever the hand is and without the band; the cross goes there in the same move. The player's sliders are not reset.

**The player's settings (`src/ui/hand-settings.ts`).** Bottom centre of the play, always visible (the debug panel, where the sliders were first, is hidden in play): the reset button and a button that opens three sliders, all remembered in the browser; a double click on a row puts it back. "Spielhöhe" (−30 … +30 cm, default 0) moves the height at which the puppet stands up or down from where it was taken (`HandTracker.height.trim`, see "Height in metres"); it comes in over 0.5 s, at 0.3 m/s at most. It has a new storage key (`hand-height-trim`): the old slider's values were metres above the floor and must not come back as a correction. "Kreuz neigen" adds up to ±45° to the cross's pitch (`pitchTrim`), for a camera that looks at the hand from above or below, or a hand held tilted because it tracks better that way; it comes on top of the rest pose. "Fadenlänge" sets `stringExtra`: longer strings and a cross further above the puppet. The puppet stands the same at any value, so it does not put the feet on the floor; that is "Spielhöhe".

**Smoothing and jumps.** Every channel goes through a One Euro filter on the frame timestamps (steady at rest, quick when moving), with small dead zones around rest; the palm's outline and the fingers are filtered before any angle is taken from them. When MediaPipe reports one hand twice, the detection that continues the tracked hand is kept (the copy is often a wrong pose with a high score). One jump was measured on the recorded session and is eased now: a hand that attaches, or comes back after more than 0.25 s, finds the cross where it was left (level, or where the hand vanished), and the cross jumped 0.4 rad at the first frame, so at every re-attach. The outputs now go over to the hand within 0.6 s. Two more are guarded against without having been seen on a real hand. Which of the two ways the palm leans (its outline allows both) is kept from frame to frame unless the evidence is clearly against it, instead of being decided anew on every frame (on a synthetic hand with noise it changed its mind up to 104 times in 20 s for a palm nearly flat to the camera). And a bar in the second hand is let go only after the hand has been seen open for 0.5 s (the four fingers nearly straight and the thumb off the index; 0.3 s until the third play test), not when its fist or pinch reading drops: a fist that moves or turns reads as open for moments (it cannot be read edge-on), and in play that let the bar go and took the other bar as soon as the fist came by its handle. The hand keeps what it holds until it opens or leaves the picture, and also when the tracker loses it for a moment: a hand that moves further between two frames than a hand can (or drops out) comes back as a new hand to the tracker, which used to drop the bar; now a second hand missing for 0.15 s is looked for anywhere in the picture, the bar is kept for 0.65 s after its hand was last seen, and a hand that shows up in that time carries on with it from where the bar is (unless it is open). The turns of a bar that has just been taken come in over 0.2 s, so it does not twitch at the grab. A hand far from the camera is small in the picture, so the same pixel of landmark noise is a larger share of the palm: below a palm length of 0.12 image heights (58 px of a 480 px picture) the filters on the outline, the fingers, the size and the tilt get slower with the palm, down to 0.35 of their cutoff. And single frames that are far off are left out: a palm outline or a finger that differs from the smoothed one by more than a real hand moves in a frame is not taken unless it stays for more than two frames. Both were tuned on the recorded session replayed smaller with noise added, which is a stand-in for how MediaPipe really fails on a far hand, not a measurement of it: at four times the distance with 1.5 px of noise the cross's tilt differs from the original by 0.03…0.04 rad (rms), and a wrist or knuckle thrown off by 6 px for one frame steps the cross by 0.06 rad instead of 0.27. A higher camera resolution (`?res=1280`) gives the landmark model more pixels of a far hand and is worth trying first. Other sudden moves seen in play are not explained yet: a `?record` session that contains one is needed (`replay-recording.mjs` lists the largest steps of the cross). The engine adds its own follower (`strings.ts`), so a step that still gets through does not whip the strings.

**Turning a held bar.** A bar in the second hand is rocked (hand bar, leg bar) or turned (head) by how far the fist has turned since it took the bar, as one angle: the turn in the picture (about the camera's axis: the bar tips as the fist is seen to tip) plus the turn of the forearm (about the hand's own long axis) as far as that axis does not point at the camera anyway. A fist is turned from the forearm; with the forearm pointing up that is no turn in the picture at all, and until the third play test the bar did not rock then (the turn in the picture alone was read exactly: 0.70 rad for 0.70 rad at any lean, on synthetic hands). The forearm's part shows only in the landmarks' depth for a palm seen flat-on and has its own, slower filter. The hand bar rocks by 1.3 times the angle (a wrist does not turn far while the hand stays closed, and waving needs one end of the bar well above the other) and takes only half of the fist's other turns. On synthetic fists, 0.6 rad turned either way gives 0.70…0.92 rad of rock at leans from 0 to 1.2 rad, the same way for both kinds of turn; held still, the bar stays within 0.04 rad. Not tried on a real hand.

**The magnet: the second hand's fist (decided).** A fist of the second hand made away from the bars' handles switches on the magnets in the puppet's hands (`grip`, both sides): a free puppet hand takes the prop in its reach (§3.2, 4) and keeps it when the fist opens. What the fist means depends on whether the puppet holds something at the fist's first closed frame (`HandTracker.puppetHolds`, set from `puppetState` before every frame). Nothing held: the magnet is on from 0.1 s after the fist is first seen until the hand is seen open. Something held: the fist is a click. Opened again within 0.6 s of its first closed frame it lets go (`release` goes up by one, the magnet is never on); kept closed longer it is the magnet again, for the other hand. The cross hand's fist does nothing of its own any more; it fades the leg bar and the head's turn as before. (Until then it was the grip, and had to stay closed for as long as the prop was held.)
- Only the fist counts (the image and the 3D landmarks agreeing, on at 0.68, off at 0.5, not read above a lean of 1.2 rad). A pinch never grabs: it is how a bar is taken.
- What keeps it from firing by accident (`TUNING.grasp`): the hand has to be seen open for 0.1 s before its fist counts, so a hand that comes into the picture closed, or back from a dropout closed, does nothing; the fist has to be seen for 0.1 s (three frames); a closure ends only when the hand has been seen open for 0.1 s, so a fist reading that dips or a hand turned edge-on keeps it; a fist within 1.6 ring radii of a handle, but outside the ring, is neither a bar nor a grab (asked on every frame until the fist counts: the fingers come in by a ring's radius while the hand closes); a hand that holds a bar or pushes the back string does only that, and a fist that is the magnet takes no bar on its way past a handle.
- A second hand lost for up to 0.5 s keeps its state (the times run on the frames' timestamps); lost for longer, the magnet goes off without a release, and what the puppet holds stays.
- Checked on synthetic hands only (`test-hand-tracking.ts`, "puppet grasp"): the magnet is on 0.17 s after the hand begins to close (it closes in 0.1 s) and off 0.2 s after it begins to open; with something held a 0.3 s fist/open gives exactly one release and a 1.5 s fist the magnet from 0.7 s on; a fist that closes on nothing and opens quickly after the puppet has caught something is no release; open frames of one and two inside a fist, a fist turned edge-on for 1 s, a hand lost for 0.3 s: the state holds; lost for 0.8 s: the magnet goes off and the returning fist does nothing until it has opened; an open hand travelling to a ring with 1.5 px of noise and single frames posed as a fist, and the back-string push: no magnet, no release. The two recorded real sessions (one hand each, with fists of the cross hand) give no magnet and no release. Not tried on a real hand: the 0.6 s window, how a fist reads at the edge of the picture, and whether a relaxed hand counts as open (a half-curled one does not: the four fingers have to be curled by less than 0.35 on average).

**Overlay.** Above the camera feed: both hands (thin; index and middle finger in the leg bar's colour, thumb and little finger in the head's) and the cross lying in the cross hand as the hand holds it: rear end at the wrist, front tip with the hand bar at the fingertips, its top towards the back of the hand, every bar rocked as it is. The handles where the second hand takes the hand bar and the head bar are rings 12.5 cm out from the main bar, on the side the second hand is on: beyond the bars' ends and clear of the cross hand, because MediaPipe loses hands that overlap. The leg bar's ring is further out and lower (22.5 cm out, 10 cm towards the palm side): its bar is only 3 cm from the hand bar. A handle is taken within 0.7 palm lengths (0.9 with two handles); where circles overlap the nearest counts (checked at cross-hand leans of 0.3, 0.9 and 1.3 rad: the nearest two handles are at least 0.15 image heights apart). The back string hangs down the picture from the rear end and bends where a hand pushes it. A dashed line marks the row of the picture at which the puppet stands for a hand at this distance, with the band around it in which the cross keeps its height, labelled "Puppe steht · Hand +3 cm" (how far the hand is above or below that height). For a new player the guided capture of that height shows in its place: the band of rows in which it is taken, and one hint at a time under the band, or just inside its lower edge where there is no room below (in impro mode the director bar lies over the window's top edge, and the meters fill its bottom), with a bar that fills while the hand holds still. A small line above the bottom right says what the height rests on ("Höhe: Hand · gesetzt · Kamera eingemessen"), highlighted while it is not sure. While the camera is measured ("Kamera einmessen"), the installer's instruction and the hold's progress take the hint's place. Also a depth gauge, meters for the leg bar and the head's turn (each from the fingers, or from the second hand while it holds that bar) and the tilt in degrees. Top right, what the magnet does: "Faust: greifen" while a prop is in reach of a free puppet hand and the second hand is free to close, "Magnet an" while its fist is the magnet, "hält: <name>" with the hint "kurz Faust auf/zu: loslassen" while the puppet holds something, and "öffnen: loslassen" with a ring that drains over the 0.6 s in which opening the hand lets go. The same is said in the line at the bottom right (what the second hand does): in impro mode the director bar lies over the overlay's top edge until the overlay is dragged away. The overlay starts at the top centre and can be dragged anywhere (the place is remembered; a double click puts it back). Under the picture a small switch sets the camera's resolution, 640 × 480 or 1280 × 720 (remembered; `?res=` wins; not shown while recording or replaying): the larger one gives the landmark model more pixels of a hand far from the camera. The running camera is asked to change, and opened anew if it does not follow; the picture's shape and crop change with it, so the tracker takes a new rest pose (as "Kreuz zurücksetzen" does), or depth and height would jump. Checked with Chrome's fake camera only.

**Record and replay.** `?record` keeps the landmark frames; R, or the button in the debug panel, downloads them as JSON (`Recording` in `src/input/hand-synthetic.ts`; saving does not stop the recording). `?replay=<url>` feeds a recording through the same pipeline instead of the camera, `?replay=synthetic` a scripted synthetic session. A recorded real session is the basis for tuning.

Recording format 2 (format 1 had the hands only, and still replays) also holds what the height model can use of the player's own body (the anchors of "Height in metres"; in play no body model runs yet):
- **Body frames.** While recording, three more MediaPipe models look at each camera frame (`src/input/body-source.ts`; what they report is typed in `src/input/body-frame.ts`, the pure file that also holds the height model): the face detector (BlazeFace short-range: six keypoints, box, score), the face landmarker (its facial transformation matrix and ten of its 478 mesh points: the eye corners, nose tip, mouth, chin, forehead and the sides of the face) and the pose landmarker (lite: 33 landmarks with their visibility). All in the raw image and rounded like the hand landmarks, about 3.4 kB of JSON per frame with everything in it.
- **`meta`.** The camera (label and track settings), the browser, which models ran on which delegate, whether the picture was mirrored, and the set-up as typed into a form in the debug panel: camera height, camera pitch (positive looks up), the player's height, the height of a mark, and notes (remembered in the browser).
- **`?record=video`** also keeps the camera's video (a `MediaRecorder`: webm, or mp4 where the browser has no webm) and saves it next to the JSON under the same name, so that models can be run on it again later. Each frame carries its `mediaTime` (from `requestVideoFrameCallback`) and `meta.video` says where the file starts on that clock; in the check below a frame was found in the file within one frame. Where the browser cannot record video, the landmarks are recorded alone and the overlay says so. The video stops after 5 minutes (it is kept in memory).

The body models exist only while recording: their code is a chunk of its own, and neither it nor the three model files are requested without `?record`. The hand tracking does not depend on them: nothing of theirs is awaited, and a model that fails is left out while the rest is recorded (`hud.body` shows which run). They are loaded once the hand landmarker has run its first frame, one after another, each with its own canvas and WebGL context (none is passed in: MediaPipe treats a canvas it is given as its own), on the GPU with the CPU as the fallback, also for a model that fails while it runs (both tried by making a model fail on purpose). What they do cost is time on the page's one thread: While recording, what they see also goes into the height model (`tracker.update(time, hands, aspect, body)`), one frame late, since they run after the tracker; a replay of the file feeds it the same way, in the page and in the script, so that the height seen while recording is the height the replay shows.
- while they compile, right after the camera starts, the hands stand still for one to two seconds (all tasks run on the main thread);
- in each camera frame the tracker gets the hands first and the body models run after it, so the frame rate drops, which a recording can afford. Headless desktop Chrome, 640 × 480 fake camera at 30 Hz: the hand landmarker ran at 29 Hz alone, at 16…22 Hz (mean 18) with all three, at 16.5 Hz with the video recorded as well, at 14…18 Hz with the three on the CPU.

`?body=face,mesh,pose` loads fewer of them (`off`: none; `cpu` in the list keeps them off the GPU), for a device that cannot run them all. The CPU delegate does not save a WebGL context (MediaPipe made four either way, counted), fewer models do.

`?record=video` has one known trap. With a video file as the camera (Chrome's `--use-file-for-fake-video-capture`), a `MediaRecorder` on the stream and a page held up for a second or more, the camera stopped for good, and the hands with it; stopping the recorder did not bring it back. Without a recorder the same hold-up did no harm, and with Chrome's built-in fake camera neither did the recorder. A real camera has not been tried. The recorder therefore starts only once the body models have loaded (their start is such a hold-up), but a later one, such as the curtain rising after a sign click, still stops a file-fed camera. Recordings are made without `=video` unless the video is wanted; with it, the frame counter in the overlay shows whether the camera still runs.

`node scripts/replay-recording.mjs <file> out.csv` runs a recording (either format) through the tracker without a browser and writes measurements and outputs per frame: among them the height (how far the hand is above the standing height, its sigma, what it rests on, the horizon row in use, the hand and the anchor above the camera's height, the body shift, the standing row, the capture's state); for format 2 also, for each body model in the file, whether it saw the player, the row of the eyes and their distance, the row of the shoulders and their width. `--pitch=<deg> --focal=<f>` replays the session as a camera pitched by that angle would have seen it: a camera that only turns sees every point along the same viewing ray, so the picture is re-projected by turning the rays about the camera's x axis, without any depth. With the matching `--horizon=<row>` (0.5 + focal · tan(pitch), printed) the height has to come out as in the level replay; without it the offset shows (the numbers are under "Height in metres"). `--horizon` is also how a measured row is tried on a recording. `--body=off|face|mesh|pose` picks which body model the height model gets to see (and which body columns are written); `--guide=0` switches the guided capture off, for comparing runs: its band is in rows of the picture, so a pitched replay may take the zero at another moment or not at all.

Checked in headless Chrome with a fake camera playing a photo of a person (face, shoulders, a raised hand), not with a real camera, a real player or a phone yet: all three models load and report (the eyes, the mesh points and the shoulders lie where the photo has them), a format 2 file replays in the page and through the script, and the format 1 recording gives the same CSV as before.

**Connecting and letting go (`src/input/hand-release.ts`):** a hand connects to the puppet as soon as it is seen above the low zone (the bottom quarter of the camera image, standing in for "hand down at the lower torso", which a hand model cannot see); a little sign asks for it while none is connected (`src/ui/release-timer.ts`). A hand that leaves the camera image for more than a second is let go: the cross stays where it is, the magnets in the puppet's hands go off (what they hold stays in them: a lost hand must not drop the prop), the bars go level, the head turns straight, the hand bar goes back on the cross and the back string is let go. When the hand that connects is a new player's (the tracker's count, see "Hand roles"; checked at the moment of connecting, because a hand enters the picture through the low zone), the puppet makes a new entrance (`flyIn`, §3.2): pulled up out of the picture and let down slowly at the new hand. It used to be dragged across the stage to the new hand and dropped there. The entrance takes 5 to 6 s (measured in the page), and the guided capture of the standing height (see "Height in metres") waits for it: `onNewPlayer` returns the entrance's promise, and before every frame the page tells the tracker whether the hand is connected at all (`HandTracker.connected`) and whether a puppet is still on its way down (`HandTracker.flying`: entrances are counted, because one that is overtaken ends early). The capture's 8 s and its second of holding still only run while connected and landed; during the flight the band shows with "Die Puppe kommt …". A script that runs the tracker alone (tests, `replay-recording.mjs`) leaves both alone: connected, not flying. The low zone stays a row of the picture. Once attached, the hand may go as low as it likes: below the standing height the strings go slack and the puppet sinks down. Until the second play test a fist held for 3 s let go of the puppet (with a 5 s countdown to take the hand away); that was taken out: lowering the hand now lets the puppet down as on a real cross, and the held fist got in the way of gripping. While no hand is connected the tracker keeps running (filters, roles) but nothing is written to `ControlInput`.

**Verified on one recorded session only** (60 s, one right hand, one webcam, made with the first mapping): the palm measures, the finger angles and the thresholds above were tuned on it. Other hands and cameras, a hand seen from the back, the head's turn by thumb and little finger (apart from the old gestures at the end of that session), the height in metres on a real camera, and everything the second hand does (taking the hand bar, the head bar or the leg bar and turning them, pushing the back string, the fist that is the magnet and the quick fist/open that lets go) are checked on synthetic hands only, not on a real hand yet. A hand far from the camera is checked on that session replayed smaller, with noise added. The height model: on synthetic scenes and on that session re-projected as from a pitched camera (numbers under "Height in metres"); in the page with synthetic hands (the capture's flow after the fly-in, the installer's step from two scripted holds, a format 2 recording with a face) and with Chrome's fake camera (the stored row of a camera, forgetting it, `?horizon=`). Not on a real camera yet: the installer's step with a real hand and how well two holds give the row, the capture's limits (band rows, palm size, lean) and its timing with a real player, and how much a real far hand's size shakes. Nothing that involves a face or a body is validated on real data.

### 3.2 Puppet rig

1. **The model defines the rig (decided):** the SKKG marionette (README, "Marionette model") comes as `export/marionette.glb` plus `export/marionette_rig.json`. The JSON holds per bone the capsule collider, `mass_kg` and the joint (cone, or hinge with a bone-local axis and limits in degrees), and the 9 strings (socket, carrying bone, position, controller point, rest length). `src/puppet/marionette.ts` turns it into a rig description; nothing about the puppet is hard-coded.
   - **Bones:** `root`, `pelvis`, `chest`, `neck`, `head`, `upper_arm/forearm/hand.L/R`, `thigh/shin/foot.L/R`.
   - **Rest pose:** arms hanging down (no T-pose), as a marionette rests on its strings.
   - **Strings:** `head.L/R`, `shoulder.L/R`, `back`, `hand.L/R`, `knee.L/R`.
   - **Control cross:** the real SKKG 9-string cross, in the JSON's `controller` section (bars with pivot, rocking axis and sticks; each string names its bar):
     - main bar (16 cm, front–back): the back string at its rear end; a fixed shoulder crossbar (11 cm);
     - head bar on a post below the shoulder crossbar, hinged in its middle: rocks about the main bar's axis by ±45° (`limit_deg`), head strings;
     - leg bar (12 cm) on a post under the middle, rocks the same way by ±50° (a full rock lifts the foot 3.3 cm; at the first 34.4° it was 2.1 cm): knee strings, walking;
     - hand bar (15 cm) at the front tip, rocks the same way: hand strings. It sits there like on a magnet and can be taken off (`detachable`).
   - **Real scale:** the puppet is 0.35 m tall; the stage is scaled to match (1.4 m wide), and so are camera, lights and props.
   - **Masses:** the real masses from the JSON with a floor of 5 % of the heaviest part, plus lead in hands and feet as real marionettes carry it (hands 12 g, feet 40 g; forearms, upper arms, shins and thighs raised with them so the joint chains stay stable). Only mass ratios show: scaling all masses alike changes nothing (measured at ×0.2 and ×5), because gravity, damping and joint friction do not depend on mass.
   - **Joints:** per bone a `cone` (swing / twist), a `hinge` (axis, min, max) or `fixed`. The feet are fixed on the shins at 90° (a marionette has no ankle joint) and the neck is fixed on the chest; the head has one joint.
2. **At runtime:**
   - one Rapier body per bone with a collider (capsule from the JSON); all bodies start unrotated, so a hinge's world axis is the same in both bodies
   - a fixed part has no body: its capsule joins its parent's body
   - joints between neighbouring bones keep the limits from the JSON: revolute joints for hinges, and for cones a generic ball joint with a limit on each rotation (set through Rapier's raw joint set, which takes limits for any axis; the JS classes only offer them on one-axis joints). Every free rotation has a little friction (a velocity motor towards 0), so limbs dangle but come to rest
   - body and head are damped more than the limbs (`STIFF` in `marionette.ts`): joint friction 30 (head), 40 (waist), 20 (hips) instead of 10, and air drag 3 on the moving of pelvis, chest and head (0.5 elsewhere) and 8 on the turning of pelvis and chest (1 elsewhere). Measured on five input steps (cross 10 cm sideways, in depth, there and back, rolled, a full leg rock), summed over eight signals: 136 s of settling time and 308 swings before, 124 s / 272 with the joint friction alone, 67 s / 157 with the drag: most of the wobble was the body swinging on its strings, which bends the joints as it goes, not the joints themselves. Knee lift, nod, head turn and hand lift are unchanged; arms and legs swing as before. What is left: on a hard sideways step the body still twists by up to 0.8 rad once (the strings force that) and is back within about 1 s
   - the solver runs 16 iterations × 4 internal ones (Rapier's default 4 × 1 let strings stretch by 3 mm in play and hinges bend 25° off their axis); 0.2 ms per step on a desktop, not measured on phones
   - the physics pose drives the `SkinnedMesh` bones
3. **Strings:**
   - each bar of the cross is a kinematic body. The main bar follows `ControlInput.bar` through a critically damped spring (0.08 s behind a steady move) with caps on speed and acceleration (12 m/s², 40 rad/s²), so a tracker spike or a hand found again elsewhere cannot whip the strings; the rocking bars ride on it and follow `ControlInput.rock` the same way, each within its own limit
   - `ControlInput.stringExtra` (default 0.15 m) makes every string that much longer and hangs the whole cross that much higher; the puppet stands the same. `bar.position` stays in rig coordinates, the engine adds the lift. It follows the setting at 0.25 m/s; the bars are set to their new height at once, not moved there, because a rope's length holds for a whole step
   - the hand bar can leave the cross: while `ControlInput.handBar.detached`, it follows that pose instead (on a leash of 0.3 m), its strings stay on it; when it is let go it drifts back onto its seat (most of the way in 0.4 s, seated after about 1 s; the first version snapped back in 0.2 s and jerked the puppet's hands), measured against the seat so it comes home while the cross moves. While it sits, the engine keeps `handBar` at the seat's pose, so a source taking it off starts from there
   - each string is a rope joint (maximum distance, rest length from the JSON), from its eye on its bar to the socket `string_<id>`
   - tilting the cross does much of the acting: sideways tilts the head and sways the body; back raises the front bars (hands and knees lift); forward lowers them and lifts the back string a little (a slight bow; a deeper bow needs the back eye further behind the pivot, both sketch estimates); rocking the leg bar walks; rocking the hand bar lifts one hand
   - hips and knees are hinges: the angled knee strings would otherwise twist the legs
   - a pull shortens the rope by setting the rope joint's length limit (at most 1 m/s); the joint is not recreated
   - a string caught by the other hand (`ControlInput.hook`) runs eye → hook → socket: the rope joint's anchor on the bar moves to the hook point and only the length below it stays free, which drags the socket towards the hook (the back string drawn 10 cm upstage at mid-length lifts the seat 2.4 cm and pitches the pelvis 48°, a bow; pushed straight sideways it swings and rolls the puppet). The push is followed like a bar, eases out on release and is capped at 0.25 m. A hooked rope, not a simulated chain of string segments: light segments between a kinematic bar and the puppet would stretch like the rubber strings that were just fixed
   - take-up of the knee strings (`TAKE_UP` in `strings.ts`): while the leg bar is level, each knee string is drawn in until it is just taut (2 mm of slack are left, so it never lifts a knee by itself) and let out again as the cross rises; while the bar rocks the length is held. The knee strings are the first to go slack when the cross sinks (1.9 cm of slack at 1 cm, 4.4 cm at 3 cm, where a full rock lifted no knee any more; the other strings stay taut, the body hangs on them), and a hand cannot hold its height to that centimetre. With it a full rock lifts the knee 3.2…4.7 cm at any height of the cross from 2 cm above its rest height to 8 cm below (the puppet sitting), half a rock about half; while the cross sinks during a step the lift is about 1 cm less. Not what a real string does: a puppeteer does it with the wrist. A taut string is let out as fast as a knee falls, and drawn in only after it has been slack for 0.15 s, so a leg that swings up is not caught there; eye and socket are compared as they are before the step (against where the bar is sent, a cross on its way down looked nearer in every step and the knees were reeled up)
   - `ControlInput.turn` (−1…1) turns the head about the vertical: the head bar turns on the cross by up to 60° (the joint stops at 70°), so its eyes stay above the head's sockets, and a spring on the twist of the head's joint stands in for the rubber strings of the real sub-cross (two plain strings 25 cm long would turn the head by a fraction of what their bar turns). Measured: 1.05 rad at ±1, 1.0 rad after 0.5 s, no overshoot; chest within 0.02 rad, head pitch within 0.03 rad. Without a turn the same spring keeps the head from twisting on the neck
   - the cross can be raised on top of the input (`setLift`, with its own pace): 1 m while a scene changes, and for a new player's puppet (`flyIn` in `puppet.ts`): the puppet on the stage is pulled up until its feet are out of the picture (about 1 s; it brakes below gravity, faster the puppet flew on past the cross and tumbled) and let down at 0.3 m/s at the new hand, which the cross follows sideways and in depth meanwhile
   - `ControlInput.nod` (0…1) lets the head strings out, as tipping a real cross forward slackens them, and the head drops forward until they hold it again: 0.41 rad at 0.5, 0.71 rad at 1 (the joint stops at 45°), chest and pelvis stay where they are; a nod takes about 0.4 s. For that the head carries lead in its face (its centre of mass 5 mm in front of its middle), as a marionette's head does: with the weight in the middle it balanced on the neck and fell back as often as forward. With the lead the head hangs 0.08 rad forward at rest. Tried and dropped, as noted during the engine work and not measured again: moving the head strings' eyes forward instead (5 cm gave half the nod and dragged chest and pelvis along)
   - the string is drawn as a sagging verlet/catenary line (rendering only)
4. **Grab, throw, drop** (`src/puppet/grab.ts`, every number in its `GRAB` table): the puppet's hands hold props like magnets. All numbers below were measured headless on the rig with a stand-in prop (a 7 cm cube of 27 g), not with a prop from the catalogue and not with a real hand.
   - **Reach:** while a hand's magnet is on (`ControlInput.grip`, a level) and the hand is free, it takes the nearest grabbable prop (dynamic, up to 0.1 m: `GRAB_SIZE` in `requisits.ts`) whose surface is within 6 cm of the hand's tip (`collider.projectPoint`; there are no sensor colliders any more). With both hands at one prop the nearer hand has it. A standing puppet's hand tips hang 13.4 cm above the floor, so a prop lower than 7.4 cm is only in reach once the puppet comes down to it (cross 3 cm lower: tips at 10.8 cm; 6 cm lower: 7.5 cm).
   - **Grip pose**, without data per prop: a box is held at the middle of its top face (8 mm inside it) and turned by the shortest way until its up axis points back along the hand, so it hangs upright below a hanging hand with its weight on the hand's axis; a ball is held where it is nearest to the hand, as it lies. A table by prop name (`GRIPS`, empty so far) can say otherwise. The fixed joint starts at the pose the two are in and is eased into the grip pose (`setLocalFrame1` for the rotation, `setLocalFrame2` for the anchor, smootherstep, 0.3 m/s and 3 rad/s, between 0.2 and 0.6 s). A cube on the floor 3.8 cm under the tip, up to 5 cm to the side, upright, tilted 0.6 rad or lying on its side: there in 0.2…0.5 s, the hand's tip at up to 0.53 m/s, the elbow at most 1.1° past its limit, the joint never more than 0.02 mm apart, the chest moved by at most 6 mm. A ball of 3 cm radius 4 cm beside the tip: held at its surface in 0.2 s. With the puppet sunk (cross 6…20 cm lower, the tip down to 0.7 cm above the floor) and the cube standing beside the hand, the pose asks the cube into the floor; what happens instead is that the hand is drawn up onto the cube (tip at 6…7.5 cm), the cube stays on the floor (at most 2 mm into it) and in the hand, the joint up to 2.2 mm apart for single steps, puppet parts at up to 1.5 m/s.
   - **While held** the prop weighs at most 3 g (its own mass comes back when it leaves the hand) and meets the stage only (`GROUP.held`: still a prop for the impact sounds). Checked on a box built as `requisits.ts` builds them (density 80, 15.4 g): 3 g while held, 15.4 g and the same inertia afterwards. At 27 g on a 12 g hand it would play the puppet, and against the puppet's body it would push what it hangs on. The cross shaken ±5 cm at 4 Hz, sideways, in depth and up and down, in two runs: the prop stays; the worst case is up and down, where the elbow goes 1.3…2.0° past its limit with the prop against 0.8…2.6° without, and the strings stretch by 0.07…0.50 mm against 0.21…0.52 mm (the runs differ by as much as the prop does).
   - **Letting go:** each change of `ControlInput.release` drops what that hand holds. The prop keeps its own velocity, times a boost that grows from 1 at 0.3 m/s to 1.5 at 0.9 m/s of the hand tip's speed against the chest, capped at 3 m/s and 12 rad/s. It cannot be taken again for 0.5 s, and the hand's magnet has to go off once before it takes anything (with the magnet still on, the prop is not taken back: checked over 4 s with the prop lying in reach). At rest the prop leaves at under 0.01 m/s sideways and lands 0.2…2.1 cm from where it was let go; in a 1 m/s sweep it leaves at 0.91…0.95 m/s against the hand's 0.88…0.90 (three runs).
   - **A full prop again** (`GROUP.prop`) only once it overlaps no other prop and no part of the puppet's body (`world.intersectionWithShape`): let go next to the leg it would be thrown out otherwise. Until then it passes through both and lies on the stage (a prop let go at rest lies at the puppet's feet until the puppet has walked on).
   - **Throwing** is a swing and a release. Let go at the top of a whip of the hand bar the prop leaves at 2.3 m/s, 0.1 s late at 0.4…1.8 m/s; the second hand's quick fist/open takes 0.2 s or more to be read, so the moment is a matter of luck.
   - **Thrown off by a whip of the free hand bar** (`GRAB.flingSpeed`, `pullMin`). The rule: the prop comes off when the hand string's eye has moved against the cross's pivot at `pullMin` or more (upwards or sideways, the most in the last 6 steps; moving the whole cross gives 0 by construction: 0.00 measured for a sweep, the scene lift and the fly-in) and the hand's tip has reached `flingSpeed` against the chest and is slowing again; not during the ease and 0.3 s after it, and not while the hand bar returns to its seat. Measured, pull / tip speed in m/s. Motions that have to hold: lifted by the hand bar rocked by key 0.33 / 0.73, by the bar raised 15 cm in 0.5 s 0.49 / 0.70 (in 0.35 s: 0.64 / 0.80), bows 0.49 / 0.27, walking 10 s with a sweep 0 / 0.65, nod, head turn and back-string push 0 / under 0.5, a sweep stopped dead 0 / 0.95, the hand bar taken 0.3 m off to the end of its leash in 0.5 s and let go 0.99 / 0.68 (0 / 0.73 while it returns, which does not count). Motions meant to throw: the hand bar whipped up at the followers' caps 1.5 / 2.13 (at 1 m/s: 0.97 / 2.11; up and forward: 1.5 / 1.36), the cross tipped back 0.6 rad 0.56 / 0.85. The tipped cross is within 1.2 times of a lift on both signals: it cannot be told from a lift and does not throw. The whips are 1.9 times above the lifts: with `pullMin` 0.7 and `flingSpeed` 1.05 (about the geometric means) every motion above that has to hold held, and the three whips threw the prop at 1.7…2.8 m/s, mostly upwards, 25…54 cm far. `GRAB.flingSpeed = Infinity` (also from the console under `?debug`) switches the throw by motion off; a throw is then a swing and a release, which is hard to time (the release gesture takes 0.2 s to read). Not tried with a real hand, whose brisk lift of the hand bar may already be a whip.
   - **Fuse:** the joint more than 2 mm apart for 3 steps, or the prop faster than 8 m/s, drops it without a boost. Only the speed fuse was seen to fire. A held prop caught under a fixed slab was pulled through it instead (joint apart up to 2.6 mm for single steps, the puppet's parts at up to 3.3 m/s): at 3 g the joint and the string win over the contact. With the cross lowered 0.2 m the prop is pressed on the floor and stays in the hand (at most 0.04 mm apart). A prop that cannot move at all (its translations locked, in a test) pins the hand: the joint stays whole, so this fuse does not see it, and the puppet's parts reached 25…59 m/s. No code path makes a held prop immovable (one that turns kinematic is let go before the step), but the fuse would not save it.
   - **When something else takes the prop:** every step the engine looks whether a held prop's body is still valid, dynamic and on the list of grabbables, and lets it go if not (mass and collision groups given back at once). That covers a scene change, a second click on the prop's card (lifted off) and the visitor's mouse drag, without `requisits.ts` knowing about hands. `hidePuppets()` drops what is held before the fade and suspends the magnets until `showPuppets()` has finished; the new player's `flyIn()` drops it before the puppet is pulled up.
   - **Feedback:** `puppetState` (what each hand holds and what its magnet would take, by the card's name), a faint golden halo at the prop in reach, brighter while the magnet is on (an additive sprite, rendering only), and a ZzFX click when a hand takes hold and when a prop comes off (`cueGrab`, `cueLetGo`).
   - **Mouse page:** F / G (or the two buttons) held are the magnets; a tap shorter than 0.3 s on a side that held something when the key went down lets go.
   - **Several puppets** (section 3.3): each has its own hands, led by its own `ControlInput` and reporting to its own state object (the local player's is `puppetState`). A prop held by one puppet cannot be taken by another; a released prop must also be clear of every puppet's body (`GROUP.clearance`) before it is a full prop again; a puppet that leaves gives the prop its mass and collision group back at once.

### 3.3 Several players (`src/net/`)

Several devices play on one stage; every device shows the whole stage. All open the same `?room=<secret>`.

**Why one device simulates.** Sending only the hands and simulating everywhere does not work: the physics is not the same on two devices (steps per frame, the step at which an input arrives), so puppets that touch each other would drift apart. One device, the **host**, runs the physics for everyone.

- **Host:** opened with `?room=<secret>&host` (without a room it makes one up and puts it in the URL). It is chosen by hand, not elected: it should be the strongest device, and there is exactly one per room. It simulates every puppet from its player's `ControlInput` and sends the poses of all bodies.
- **Clients:** every other device. They send their `ControlInput` and show the poses they receive. Their puppets are kinematic bodies without joints or colliders, set from the network; bones, strings and follow spots work as for a simulated puppet, because they only read body poses.
- **IWSDK has no networking** (its guide leaves realtime multiplayer to the app), so this is our own layer, next to Rapier.

**Transport** (`transport.ts`): **Trystero** (pinned), Nostr strategy. A page cannot discover devices on a LAN, so peers need a place to meet: public Nostr relays carry the WebRTC handshake, encrypted with the room id as password; after that the devices talk directly. The rest of `src/net/` only knows a small `Transport` interface.

- **Reliable messages** (JSON, Trystero action): who plays what, the stage set.
- **Pose packets** (binary): over our own second data channel on the same connection, unordered and without retransmits (`negotiated`, so Trystero does not see it), because on a congested Wi-Fi one lost packet would otherwise hold back all later ones. Used only after the other side answered on it; until then, and with `&lossy=0`, pose packets use Trystero's ordered channel.
- **Fallbacks** when a network blocks direct connections: TURN (`VITE_TURN_URLS`, `VITE_TURN_USERNAME`, `VITE_TURN_CREDENTIAL`), or a second `Transport` implementation: a WebSocket relay as a Vite plugin (not built).

**Messages** (`protocol.ts`):

| Message | Direction | Rate | Size | Channel |
|---|---|---|---|---|
| Input: the whole `ControlInput` (also the string length, a caught string, nod, head turn and the release counters), with a sequence number | client → host | 60 Hz | 74 B | pose |
| Puppet: its slot, the host's physics step, the pose of every body (bars, then bones) | host → all | 30 Hz | 244 B per puppet | pose |
| Roster: peer → puppet slot | host → all | on change, repeated every 2 s | small | reliable |
| Hands: what a player's puppet holds and could take (`puppetState`) | host → that player's device | on change, 10 Hz at most | small | reliable |
| Stage: the backdrop | whoever changed it → all; host → a device that joins | on change | small | reliable |
| Bye | a closing page → all | once | small | reliable |

- Poses are absolute (16-bit positions in 0.2 mm steps, 16-bit quaternions); an older or repeated packet is dropped. One packet per puppet keeps each far below the size at which packets are split.
- Bodies are told apart by their place in a list that is the same on every device (the cross's bars in rig order, then the bones), never by Rapier handle.

**On a client** (`session.ts`): poses are shown 73 ms in the past, blended between two snapshots, never guessed ahead. From an input to the player's own cross moving on screen: about 100 ms plus the network's round trip (measured: 97 ms on one machine, until the cross first moves; the engine's follower then trails the input by about 80 ms, as it does for a single player). After 0.5 s without poses the client shows "Bühne pausiert": the host's physics runs in its render loop and stops when its tab is hidden.

**Puppets on the stage:** up to six, each in its own slot: a starting place, and its own collision group, so a puppet's parts ignore each other but bump into other puppets (`&contact=0` on the host: they pass through each other). A puppet is removed when its player leaves; what it held stays on the stage as a full prop.

**Hands** (section 3.2, 4) are part of the physics, so every puppet's hands are on the host, led by its player's `grip` and `release`. A prop is in one hand at a time, whichever puppet's: which props are held, just released or not yet clear is kept for all puppets together (`grab.ts`). The host writes its own player's `puppetState` directly and sends every other player theirs (the Hands message): the hand tracking needs it to tell a grip from a release, and the HUD shows it.

**Shared stage set:** only the backdrop, whoever sets it and however: the impro panel, a scene preset, or the Stücke button, which clears it for everyone.

**Not shared:**
- The main curtain, the signs and the chosen play. Every device clicks a sign itself, because that click is the user gesture its camera needs.
- **Props and scene presets** (`src/props/requisits.ts`, `src/plays/`). Each device sets its own props; only the host's are in the physics, so puppets bump into props the clients do not see, and a client's props are scenery its puppets pass through. A scene change moves the props on that device only; on the host it also pulls every puppet up for the change, on a client the puppets only fade. Until the props are shared (open: the host owns the set, the others ask it), use props in a room on the host only, or not at all.
- Light and sound.

**Different on a client:** a string caught by the other hand (`hook`) is drawn straight, and the strings of other players' puppets sag as for the default string length. The puppets make no impact sounds there: they have no colliders, so only the host hears them clatter; the same goes for the halo at a prop in reach and the click of the magnet. A new player's hand does not make the puppet fly in (`flyIn()` moves only a puppet that is simulated on the device, and only the local player's: on the host the other players' puppets stay where they are).

**Later, over the same room:** an AI player (simplest as another `ControlInput` writer on the host, without the network); XR players (a controller or hand is another `ControlInput` source; showing where they stand needs a presence message); audience directions (dozens of phones cannot join a mesh in which everyone connects to everyone, so they need another path: the relay, or publish/subscribe on the meeting infrastructure); host election; a QR code for the join link.

## 4. Asset pipeline

The sources are committed in `/assets`, grouped by where they come from (e.g. `assets/digital.skkg.ch/Stuhl_25210.6.{blend,glb,jpg}`: the original photo, the Blender file and a `.glb`). Large files (over about 20 MB) are not committed: they live on external storage and everyone downloads them by hand into `assets/external/<source>/`, which is git-ignored except for its README (`assets/external/README.md`, with the storage location). No git LFS.

**Now:** there is no build step for assets. The code imports them from `assets/` directly (`?url` imports, `import.meta.glob`), and Vite serves and bundles them as they are. Scripts fill in the rest: `scripts/fetch-mediapipe-models.sh` (MediaPipe models into `public/mediapipe/`: the hand landmarker for play, and the face detector, face landmarker and pose landmarker that only `?record` loads), `scripts/unpack-sounds.sh` (sound effects, runs before `dev` and `build`), `scripts/index-archive.mjs` (archive.org metadata).

**Later, the `convert` service** (Docker): it would read `assets/` and `assets/external/` and write optimized files to `/public` (git-ignored) plus `public/manifest.json`, incrementally (source hashes), with `--watch` in dev.

| Source | Tool (in the container, later) | Output |
|---|---|---|
| `.blend`, `.fbx`, `.obj` | Blender headless (`blender -b … --python export.py`) | `.glb` with skeleton and `string.*` empties |
| `.glb/.gltf` + Blender output | `gltf-transform` (meshopt, KTX2/WebP) | optimized `.glb` |
| Paper sheet scans | `sharp` + `gltf-transform` | alpha quad `.glb` |
| Audio | ffmpeg | `.m4a` (+ `.webm`) |
| Geist Serif | typeface conversion | JSON for `TextGeometry` |

## 7. Risks

- **Rapier next to IWSDK:** IWSDK's own physics stays off. If we later want IWSDK features that assume its physics (e.g. its grabbing in XR), they will need an adapter to our Rapier bodies.
- **MediaPipe and rendering together on a mid-range phone:** performance needs to be measured in phase 0. Possible measures: lower camera resolution, inference at 15–30 Hz.
- **Blender in Docker on Apple Silicon** (once the converter exists) runs under x86 emulation and is slow. A local `BLENDER_BIN` is the fallback.
- **A second model for the hand's height (a face or a body), later:** in play only the hand landmarker runs. The height model can already read a face or a body ("Height in metres"), but running one costs frame rate on the page's one thread (while recording, the hand landmarker fell from 29 Hz to 16 … 22 Hz with three body models; a face detector alone, on a stride of frames, is the candidate) and a WebGL context per task. And what it would add rests on assumptions (the hand plays 42 cm below the eyes; the eyes' distance as a ruler, which a face 14 px wide with 2 px of noise no longer is) until recordings with a face or a body in them exist. Until then a pitched camera needs the installer's step ("Kamera einmessen"), and without it the height drifts with the hand's distance.
- **iOS permissions:** camera, DeviceOrientation and audio all need a user gesture, which the Play button provides.
- **Self-signed certificates:** phones warn once. For the demo, use a real certificate on the server.
- **Multiplayer on the venue's Wi-Fi:** not yet tested on real devices. Direct connections fail on networks with client isolation, or where devices only tell each other `.local` names that the network does not resolve (browsers hide the LAN address unless the page has camera permission; Quest ↔ laptop is the hard case). Then TURN or the WebSocket relay is needed (section 3.3). A VPN as the default route does the same even between two tabs on one machine (seen while testing: no connection until the tabs had camera permission, with which the browser offers every network interface). Whether a data channel survives entering VR on a Quest 2 is also untested.
- **Multiplayer needs the internet** to meet (public Nostr relays), also on a LAN.
- **The host carries everyone:** it simulates up to six ragdolls (measured: 2.1 ms per step at worst for two puppets in contact, on a desktop), and a hidden host tab stops every stage.
